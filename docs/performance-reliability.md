## 本轮首次发现的问题

1. 重复翻译请求同时到达时，先查询再插入存在竞争，8 个请求实测 1 个 202、7 个 500。
   JobRepository 改用 PostgreSQL 唯一约束和 `INSERT ... ON CONFLICT DO NOTHING` 仲裁。
2. Nginx 默认把限流返回成 503；128 请求突发实测为 46 个 200、82 个 503。
   现配置明确的 429 JSON 错误与 Retry-After。
3. 领域层非法命令原来透传为 500。命令入口现捕获 CommandConflict，返回 422，
   保留完整的原版本和事务原子性。每项均先保留真实失败回归，再部署修改后复测。
4. 原有断线恢复旅程出现 Agent 初始计划混入过多素材库片段、两轮后仍超出比例的失败。
   原片与素材库同时存在时，现在也会进入已有的原片范围选择修复；范围由真实模型选择，
   再用原生领域命令与实测来源边界校验。新增最小回归先失败、修复后通过。
5. 队列租约组件测试与常驻 Worker 曾争抢公开测试表中的任务。队列组件测试改在实际
   PostgreSQL 的独立临时数据库运行，结束后删除该库；API 并发测试继续经过真实常驻队列。
6. 浏览器导出发现已保存的背景音乐长于可见视频，直到渲染才失败。规划阶段现在按原生
   编译器相同的帧换算检查音轨和字幕末尾，越界计划在保存前进入有界修复。
   原生编译器继续保留最终校验；对应音轨/字幕两项回归先失败、修复后通过。
7. 项目数量超过第一页的 50 条后，刷新可能找不到刚创建的项目。前端现在沿游标加载
   后续页面，复用每页的会话展开结果，并拒绝重复游标，保留原有工作台样式。
8. 多轮修改曾删除原片或重复创建已有片段。此类失败的修复调用只允许调整现有片段，
   用 schema 枚举约束可引用编号，并提供原始时间线边界；裁剪产生的原字幕先由原字幕
   节点对齐，再检查最终边界，避免误拒合法裁剪。

业务耗时汇总排除明确取消并重试的翻译样本，其完整生命周期另行保存在原始批次记录中。

字幕下移后的 60 秒、1080p、standard 样片实测排队 0.904 秒、执行 50.684 秒、
